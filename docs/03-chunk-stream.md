# 03. チャンクストリーム層詳解

> 対応ソースコード: `pkg/chunk/chunk.go`

## チャンクストリーム層とは

RTMPメッセージ（音声・映像・コマンドなど）をTCP上で効率的に送受信するための
**多重化・分割レイヤー**。RTMPの中核を担う最も複雑な部分。

## なぜチャンクに分割するのか

### 問題: Head-of-Line Blocking（先頭ブロッキング）

もしメッセージをそのまま送ると、以下の問題が起きる:

```
大きな映像フレーム（100KB）を送信中...
├────────────────────────────────────────┤
                                          ↑ 映像フレームの送信が完了するまで
                                            音声パケット（200B）が待たされる
                                            → 音声が途切れる！
```

### 解決: チャンク分割による多重化

メッセージを小さなチャンクに分割し、交互に送ることで解決:

```
映像チャンク1 → 音声チャンク → 映像チャンク2 → 映像チャンク3 → 音声チャンク → ...
├──128B──┤   ├──128B──┤   ├──128B──┤   ├──128B──┤   ├──128B──┤
```

こうすることで、大きなメッセージが小さなメッセージをブロックしない。

## チャンクの全体構造

1つのチャンクは以下の3つの部分から成る:

```
+-------------------+-------------------+-------------------+
| Basic Header      | Message Header    | Chunk Data        |
| (1〜3バイト)      | (0/3/7/11バイト)  | (最大chunkSizeバイト) |
+-------------------+-------------------+-------------------+
```

## Basic Header（基本ヘッダ）

チャンクの先頭にある1〜3バイトのヘッダ。
**フォーマットタイプ（fmt）** と **チャンクストリームID（csid）** を含む。

### 1バイト形式（csid: 2〜63）

```
 ビット: 7 6 5 4 3 2 1 0
       +-----+-----------+
       | fmt |   csid    |
       +-----+-----------+
         2bit    6bit

例: fmt=0, csid=3 → 0b00_000011 → 0x03
例: fmt=3, csid=6 → 0b11_000110 → 0xC6
```

### 2バイト形式（csid: 64〜319）

```
バイト1: [fmt(2bit)][000000]    ← csid部分が0
バイト2: [csid - 64]

実際のcsid = 64 + バイト2の値
```

### 3バイト形式（csid: 64〜65599）

```
バイト1: [fmt(2bit)][000001]    ← csid部分が1
バイト2: [(csid-64)の下位8ビット]
バイト3: [(csid-64)の上位8ビット]

実際のcsid = 64 + バイト2 + バイト3×256
```

### チャンクストリームIDの意味

| csid | 用途 |
|---|---|
| 0 | 2バイト形式のマーカー（csidではない） |
| 1 | 3バイト形式のマーカー（csidではない） |
| **2** | **プロトコル制御メッセージ用（TypeID 1〜6）** |
| **3** | **コマンドメッセージ用（connect, publishなど）** |
| **4** | **音声データ用** |
| **6** | **映像データ用** |

**対応するソースコード:**

```go
// pkg/chunk/chunk.go - Basic Headerの読み取り
firstByte, _ := cr.r.ReadByte()
hdr.Fmt = (firstByte >> 6) & 0x03   // 上位2ビット = fmt
csid := uint32(firstByte & 0x3F)     // 下位6ビット = csid

switch csid {
case 0:  // 2バイト形式
    b, _ := cr.r.ReadByte()
    hdr.ChunkStreamID = uint32(b) + 64
case 1:  // 3バイト形式
    buf := make([]byte, 2)
    io.ReadFull(cr.r, buf)
    hdr.ChunkStreamID = uint32(buf[0]) + uint32(buf[1])*256 + 64
default: // 1バイト形式
    hdr.ChunkStreamID = csid
}
```

## Message Header（メッセージヘッダ）

**fmt（フォーマットタイプ）** の値によってサイズが変わる。
これがRTMPの **ヘッダ圧縮** の仕組み。

### Type 0（11バイト）— 完全ヘッダ

ストリームの最初のチャンクや、前回と大きく異なるメッセージに使う。

```
+------------------+------------------+----------+------------------+
| timestamp        | message length   | type ID  | message stream ID|
| (3 bytes, BE)    | (3 bytes, BE)    | (1 byte) | (4 bytes, LE !!) |
+------------------+------------------+----------+------------------+
```

| フィールド | サイズ | エンディアン | 説明 |
|---|---|---|---|
| timestamp | 3バイト | ビッグ | メッセージのタイムスタンプ（ms） |
| message length | 3バイト | ビッグ | メッセージ全体のバイト数 |
| type ID | 1バイト | — | メッセージの種類（1=ChunkSize, 8=Audio, 9=Video, 20=Command） |
| message stream ID | 4バイト | **リトル** | アプリケーション層のストリーム識別子 |

> **注意**: message stream ID だけが **リトルエンディアン**。
> RTMP全体ではビッグエンディアンが基本だが、この部分だけ例外的にリトルエンディアン。
> これはRTMPの仕様における有名な罠のひとつ。

### Type 1（7バイト）— ストリームID省略

同じメッセージストリームIDの後続メッセージに使う。

```
+------------------+------------------+----------+
| timestamp delta  | message length   | type ID  |
| (3 bytes)        | (3 bytes)        | (1 byte) |
+------------------+------------------+----------+
```

message stream ID は前回のチャンクの値を引き継ぐ。

### Type 2（3バイト）— タイムスタンプ差分のみ

メッセージ長とタイプIDも前回と同じ場合に使う。

```
+------------------+
| timestamp delta  |
| (3 bytes)        |
+------------------+
```

### Type 3（0バイト）— ヘッダなし

前回のチャンクと全て同じ属性の場合、または同一メッセージの継続チャンク。
Basic Headerのみで、Message Headerは一切付かない。

```
(Message Header なし = 0バイト)
```

### ヘッダ圧縮の効果

映像データの連続送信を例にすると:

```
チャンク1: [Basic(1B)] [Type0(11B)] [Data(128B)]  ← 最初は完全ヘッダ
チャンク2: [Basic(1B)] [Type3(0B)]  [Data(128B)]  ← 継続チャンクはヘッダなし
チャンク3: [Basic(1B)] [Type3(0B)]  [Data(128B)]  ← ヘッダなし
チャンク4: [Basic(1B)] [Type3(0B)]  [Data(44B)]   ← 最後のチャンク

合計: 元メッセージ428B → チャンク合計 428 + 12 + 3 = 443B（オーバーヘッド約3.5%）
```

## Extended Timestamp（拡張タイムスタンプ）

タイムスタンプが **0xFFFFFF（16,777,215）以上** の場合に使う。

```
通常のタイムスタンプ（3バイトに収まる場合）:
  Message Header内のtimestampフィールドにそのまま格納

拡張タイムスタンプが必要な場合:
  1. timestampフィールドに 0xFFFFFF を格納
  2. Message Headerの直後に4バイトの拡張タイムスタンプを追加

+---Message Header---+---Extended Timestamp---+---Chunk Data---+
| ...timestamp=FFFFFF | (4 bytes, BE)          | ...             |
+--------------------+------------------------+-----------------+
```

0xFFFFFF ミリ秒 = 約4.66時間。つまり4時間半以上の配信では拡張タイムスタンプが必要。

## チャンクサイズ

### デフォルト: 128バイト

RTMP仕様のデフォルトチャンクサイズは128バイト。しかしこれは非常に小さく、
映像フレーム（数十KB）を送ると大量のチャンクヘッダが発生してオーバーヘッドが大きい。

### 実用的な値: 4096バイト

多くのサーバーはconnect応答時に **Set Chunk Size** メッセージを送り、
チャンクサイズを4096バイト以上に変更する。

```
128バイトの場合:  10KBのメッセージ → 79チャンク → ヘッダ79回分のオーバーヘッド
4096バイトの場合: 10KBのメッセージ → 3チャンク  → ヘッダ3回分のオーバーヘッド
```

**対応するソースコード:**

```go
// server/server.go - connectハンドラ内
csHdr, csBody := message.NewSetChunkSize(4096)
c.writer.WriteMessage(csHdr, csBody)
c.writer.SetChunkSize(4096) // 送信側のチャンクサイズを変更
```

## メッセージの分割と再構築

### 送信側（Writer）

1. メッセージ全体を `chunkSize` バイトごとに分割
2. 最初のチャンクには Type 0 ヘッダ（完全ヘッダ）を付ける
3. 後続のチャンクには Type 3 ヘッダ（ヘッダなし）を付ける

```
元のメッセージ（500バイト、chunkSize=128）:
  チャンク1: [Type0] [128バイト]
  チャンク2: [Type3] [128バイト]
  チャンク3: [Type3] [128バイト]
  チャンク4: [Type3] [116バイト] ← 残り
```

### 受信側（Reader）

1. チャンクヘッダを読み取る
2. csidに対応する状態（前回のヘッダ情報、受信中のバッファ）を参照
3. fmtに応じて不足しているヘッダ情報を前回の値で補完
4. チャンクデータを受信バッファに追加
5. メッセージ全体の長さに達したら、完成したメッセージを返す

**対応するソースコード:**

```go
// pkg/chunk/chunk.go - ReadMessage
func (cr *Reader) ReadMessage() (Header, []byte, error) {
    for {
        hdr, _ := cr.readChunkHeader()
        state := cr.prevState[hdr.ChunkStreamID]

        // fmtに応じてヘッダ情報を補完
        switch hdr.Fmt {
        case 0: // 全フィールドが含まれる
        case 1: // MessageStreamIDは前回の値
        case 2: // Length, TypeID, StreamIDは前回の値
        case 3: // 全て前回の値（継続チャンク）
        }

        // チャンクデータを読み取ってバッファに追加
        chunkData := make([]byte, readSize)
        io.ReadFull(cr.r, chunkData)
        state.body = append(state.body, chunkData...)
        state.remaining -= readSize

        // メッセージが完成したら返す
        if state.remaining == 0 {
            return hdr, state.body, nil
        }
        // まだ完成していなければ次のチャンクを読む
    }
}
```

## 多重化の具体例

映像と音声のチャンクが1本のTCPストリーム上でインターリーブされる:

```
TCP バイトストリーム:
┌────┬────┬────┬────┬────┬────┬────┬────┐
│V-1 │V-2 │A-1 │V-3 │V-4 │A-2 │V-5 │A-3 │
└────┴────┴────┴────┴────┴────┴────┴────┘
 csid=6  csid=6  csid=4  csid=6  csid=6  csid=4  csid=6  csid=4

V = 映像チャンク (csid=6)
A = 音声チャンク (csid=4)
```

受信側は csid を見てどのストリームのチャンクかを判別し、
それぞれのバッファに追加して元のメッセージを再構築する。
